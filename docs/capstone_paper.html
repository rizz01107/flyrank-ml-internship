Refresh-Priority Scoring: Finding the Content Worth Fixing First

By Muhammad Rizwan · GitHub repo · Portfolio

Abstract

Which of a client's declining pages are worth fixing first, and can a learned model rank that priority better than a hand-written rule? Using 15 days of early-month search performance to predict 15-day-later click decline, I built a client-grouped Random Forest and compared it against a CTR-gap baseline on the same held-out test set. The model improved Precision@50 from 0.46 to 0.62 and Precision@20 from 0.55 to 0.65 over the baseline. Error analysis showed the model relies almost entirely on CTR and click signals, and its failures cluster around a single client whose pages sit at very poor average search positions — suggesting per-client normalization as the clearest next improvement.

1. Introduction / Problem Statement

Content teams managing large page inventories face a recurring decision: with limited time, which declining pages should be reviewed and refreshed first? A blanket "everything below X% CTR" rule treats every stale page identically, ignoring how much traffic is actually at stake and how a page's position interacts with its click-through performance.

This work supports one decision: ranking content-refresh priority so that a content team's limited review time goes to the pages where a fix is most likely to matter, rather than being spent in query order or by gut feel.

2. Data

Data comes from the FlyRank ML Internship warehouse release (Hugging Face, gated access), specifically the fact_content_daily_performance table for month=2026-03 — a mid-panel month, chosen deliberately over the final month of the release, which is reserved as a sealed test window and never used for label logic.

Unit of analysis: one row is one (client, content page, date) daily search-performance record. After filtering to rows with gsc_data_available IS TRUE and at least 50 impressions in the first 15 days of the month, the working set was 92,247 (client, page) pairs, spanning 39 distinct clients.

Excluded fields, and why

  • AI-referral columns (ai_chatgpt, ai_claude, ai_gemini, etc.) — excluded because AI-referral sessions are sparse per client/page and unreliable as a per-page signal at this grain.
  • scroll_events — excluded because it is behavioral and not consistently available across all pages.
  • Any post-day-15 signal as a feature — excluded from the feature set entirely, since it would leak information from the label's own time window (see Methodology).

3. Methodology

Label definition

A page is labeled declining if its total clicks in the second half of the month (days 16–31) are lower than its clicks in the first half (days 1–15). This is a same-month proxy built for methodological clarity, not a true forward-looking outcome — a genuinely predictive version would need a separate future month, which the capstone's single-month scope did not use.

Features (all knowable at the day-15 decision point)

  • imp_first15, clk_first15 — total impressions and clicks, days 1–15
  • avg_position_first15 — average search position, days 1–15
  • ctr_first15 — click-through rate, days 1–15
  • has_ga4 — whether the client has GA4 data available

Baseline

A hand-written rule: score = max(0, expected_ctr_for_position − actual_ctr) × impressions, where expected CTR by position tier was derived empirically from the same dataset (confirmed CTR drops monotonically from 0.48% at positions 1–3 to 0.13% at positions 21+).

Model

A RandomForestClassifier (200 trees, max depth 6, class-balanced), trained on the same five features.

Validation design

Split via GroupShuffleSplit, grouped by client_hash_id — a client's pages never appear in both train and test, preventing the model from learning client-specific quirks instead of generalizable signal. Confirmed zero client overlap between the 87,202-row train set (29 clients) and 5,045-row test set (10 clients).

Leakage check

As a deliberate audit (not part of the final model), a feature built from the label's own time window was added to a test model. Honest AUC was 0.782; with the leaky feature added, AUC jumped to 1.000 — a clean demonstration of how label-window leakage silently produces unusable, falsely perfect results. The leaky feature was removed and never used in the reported model.

Feature importance (permutation)

The model relies almost entirely on ctr_first15 and clk_first15 (importance ≈0.047 each); imp_first15, avg_position_first15, and has_ga4 contributed close to zero, or even slightly negative, importance.

Error analysis

Of the model's top-20 ranked predictions, 8 were incorrect (flagged high-risk, not actually declining) — and all 8 wrong picks came from a single client whose pages sit at very poor average positions (40–70). This suggests the model may under-weight position for clients whose baseline performance is already low, treating a stable-but-low click pattern as decline.

5. Limitations & Honest Framing

  • All findings are observed and directional, not causal — this work does not claim to explain or predict Google's ranking algorithm.
  • The label is a same-month proxy, not a genuinely forward-looking outcome; a production version would need a held-out future month.
  • Client history is unbalanced (different clients have different amounts of usable history), so a single mid-panel month may not represent every client equally.
  • The model's errors concentrate in one client's low-position pages — this is a decision-support tool that still needs human review before any page is actually deprioritized.

6. Ranked Recommendations

1

Prioritize high-impression pages where CTR sits well below the position-adjusted expectation — these carry the largest absolute opportunity per fix, per the model's dominant CTR/click signal.

2

Flag pages with near-zero CTR at very poor average position (40+) for manual content review rather than an automatic title/snippet rewrite — these are more likely an intent mismatch than a fixable snippet problem, based on the client-specific error pattern observed.

3

Before trusting a ranked list for any one client, check whether that client's pages skew toward poor average position — the model's accuracy was uneven across clients in this evaluation, and a per-client normalization pass is the clearest next step.
